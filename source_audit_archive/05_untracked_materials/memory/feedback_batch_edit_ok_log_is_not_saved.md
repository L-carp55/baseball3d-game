複数の置換をメモリ上で行い、最後にまとめてファイルへ書き出すスクリプトは、**途中で例外が出ると、それまでの「ok」を全部出したうえで1つも保存されない**。ログだけ見て「適用した」と報告すると、実際には何も変わっていない。

2026-08-01の野球ゲームで発生。6件の置換のうち3件が「ok」と出た後、4件目でパターン不一致により中断。ファイルは無変更なのに、3件を適用済みとして次の検証に進み、結果が変わらない理由を別の場所に探して時間を溶かした（さらに一時は「外部プロセスがファイルを書き換えた」と誤診しかけた）。

**同日中に2回目が発生（2026-08-01夕）**: 同じ型で `armEff` の**定義だけが保存されず、それを呼ぶ側のコードだけが残った**。この状態は**構文チェックを通る**（未定義関数の呼び出しは実行時エラー）ため、「構文OK」を見て安心し、実行して初めて `armEff is not defined` で気づいた。**構文が通ることは保存の証拠にも整合の証拠にもならない。**

**Why:** 進捗ログは「メモリ上の文字列が置換された」ことしか示さない。ディスクへの反映は最後の1回の書き込みで、そこに到達しなければ全部無かったことになる。人もAIも「okが並んでいる＝終わった」と読むので、失敗が静かに通過する。

**How to apply:**
1. **保存した直後にファイルを読み直し、目印の文字列が存在するかを確認して出力する。** スクリプトの末尾に検証ブロックを必ず置く（`for k in [...]: print('OK' if k in reread else 'MISS', k)`）。
2. 置換ごとに**即時保存**するか、失敗時に**部分保存しない旨を明示**する。どちらでもよいが、どちらなのかを自分で把握しておく。
3. 検証は**別プロセス／再読込**で行う。同じメモリ上の変数を見ても、保存されたかは分からない。
4. 挙動が変わらない時、**まず「本当に保存されたか」を疑う**。実装の理屈を疑うのはその後。順番を逆にすると、存在しない原因を探すことになる。
5. 同じ型: サーバー経由で確認する時のキャッシュ。今回もブラウザが古いHTMLを返し、修正が効いていないように見えた（クエリ文字列を変えて再取得で解決）。**「直したのに変わらない」の第一候補は、保存とキャッシュ**。
